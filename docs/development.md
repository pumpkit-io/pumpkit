# Development guide

## Project layout

```
backend/src/pumpkit/
  main.py          the FastAPI app: mounts every area's router and the MCP endpoint, and registers the error handlers
  mcp_server.py    the MCP server: every area's tools behind API key authentication, the access gate and per-User limits
  models.py        imports every area's models, so Alembic and the tests see the whole schema
  core/            plumbing every area shares: config, logging, db/ (base, session, URLs), errors, security, rate limiting, analytics, time, ids, MCP tools, the classifier port (Jev), the photo-fetching port
  auth/            Users, Sessions, refresh tokens, Google identities, Magic links; Google sign-in, the auth mailer and its templates/
  billing/         Plans and Subscriptions; the billing gateway (Stripe) and the Stripe webhook
  authors/         Inspiration authors, their posts and the Author directory; the X reader (twitterapi.io)
  x_connection/    X connections; the X publisher port (X's API) and X's weighted length count
  support/         the support contact redirect (a router only)
  posts/           Posts and Versions; the LLM port and OpenAI-compatible client
  onboarding/      where the web app sends a signed-in User next: the Paywall, then Onboarding
  posts/writing/   the pumpkit-v6 writing workflow: prompts, corpus framing, scrub, writing a Version
  scheduling/      Scheduled posts: rules, publish steps, publishing, and the publisher process
backend/tests/     pytest suite, mirroring the package tree; fixtures in conftest.py
frontend/src/
  features/        self-contained feature modules (account, analyticsConsent, apiKeys, billing, inspirationAuthors, instance, legal, onboarding, posts, scheduledPosts, sidebar, theme, topbar, xConnection)
  components/      shared UI: auth, blocks, brand, ui primitives, the Settings card
  services/        API clients (apiService handles tokens and refresh)
  lib/             analytics, storage, app constants and helpers
  pages/           route-level pages: NewPost, Posts (one tab per status), PostPage, Persona, Settings, Paywall; AppLayout and layout/ (the signed-in shell), OnboardingLayout (the focused shell before it); signedInRoutes.tsx (the route table)
  contexts/        auth context
e2e/               Playwright tests run against compose.dev.yml
infra/web/         the web image: Dockerfile, Caddyfile, start-up steps, PostHog relay snippet
scripts/           setup.sh (writes .env), check-stack.sh (smoke checks), the release scripts
docs/              configuration, self-hosting, releasing, ADRs
```

Every area is built from the same modules: `router.py` (HTTP only: dependencies, parsing, response shaping), `mediator.py` (orchestration and the transaction), `service.py` (one resource or capability each, with its database access), `schemas.py` (Pydantic request and response models) and `models.py` (SQLAlchemy tables). An area with nothing to orchestrate skips the mediator, and `support` is a router alone. The call direction is `router -> mediator -> service`, never backwards, and no DB queries in routers or mediators.

The signed-in web app is one route table, `pages/signedInRoutes.tsx`. `OnboardingProvider` (`features/onboarding/`) reads `GET /api/v1/onboarding` on every sign-in and page load, and each layout sits behind an `OnboardingGate` that sends the User to the page their `next_step` is on (ADR 0018): `/subscribe` for `paywall`, `/onboarding` for an Onboarding step, else the app. `/` routes the same way, after greeting a return from checkout. The step is never in the URL.

- `/subscribe` (`pages/Paywall.tsx`): the Paywall, inside `pages/OnboardingLayout.tsx` (no sidebar: the wordmark, the step indicator, the account menu and the legal links). It offers the Plans through `features/billing/PlanPicker.tsx`, with the Terms boxes.
- `/onboarding` (`pages/Onboarding.tsx`): the Onboarding step `next_step` names, in the same shell. The X step (`features/onboarding/XStep.tsx`, `next_step` `x_connection`) comes first on an Instance with X and while the User has no X connection; it starts an authorization and asks `GET /onboarding` again whenever the tab regains focus, since X may have been connected in another tab. The X callback (`pages/XConnectionCallback.tsx`) asks `GET /onboarding` after completing: while Onboarding isn't finished it returns to `/onboarding` with the outcome in the location state (the connected account, shown for a moment before the next step, or the reason it failed), and to Settings with its notice otherwise. The Persona step (`features/onboarding/PersonaStep.tsx`) is the Persona page's `InspirationAuthorsPanel` with Continue, which calls `POST /api/v1/onboarding/finish`; the gate then sends the finished User to New post. The `onboarding` area stores only that a User finished (ADR 0018), so emptying the Persona later never sends them back.

Every other page renders inside `pages/AppLayout.tsx` (the providers, the sidebar and the Reconnect X banner):

- `/new` (`pages/NewPost.tsx`): the Brief and Format form, `features/posts/PostWriter.tsx`.
- `/posts/scheduled`, `/posts/drafts`, `/posts/published` and `/posts/failed` (`pages/Posts.tsx`): one tab per status, built from `features/posts/list/`. `/posts` opens the Scheduled tab.
- `/posts/:id` (`pages/PostPage.tsx`): the Text card (`features/posts/TextCard.tsx`) and, pinned below it, one dock per status from `features/posts/panels/`; the "Post to…" dialog is `features/posts/postTo/` and the inline edit of a Scheduled post is `features/posts/edit/`.
- `/persona` (`pages/Persona.tsx`): the Inspiration authors, `features/inspirationAuthors/`.
- `/settings` (`pages/Settings.tsx`): one card each from `features/billing/` (Plan), `features/account/` (Profile), `features/xConnection/` (X account), `features/apiKeys/` and `features/theme/` (Appearance).

`features/scheduledPosts/` keeps what those pages share about Scheduled posts: Destinations and Communities, the X length counter, live Parts and local time.

ADR 0008 orders the areas `core` <- `auth` <- `billing` <- {`authors`, `x_connection`, `support`} <- {`posts`, `onboarding`} <- `scheduling`: an area imports only areas to its left, and only their service, models, schemas and domain modules, never a router or mediator. `core` imports no area. `cd backend && uv run --extra dev lint-imports` checks these rules with the contracts in `backend/pyproject.toml`, and CI runs it. When an endpoint belongs to one area but needs a higher area's data, serve it from the higher area: `GET /x-connection` and `POST /x-connection/authorizations/complete` answer with the count of waiting Scheduled posts, so `scheduling/router.py` serves them, and `x_connection/router.py` keeps starting an authorization, disconnecting, and using or declining the X account's photo as the User's Photo.

## Recipes

### Subscriptions

Pumpkit bills by Subscription (see `docs/adr/0003-subscription-only-billing.md`), and sells one thing outside it, the Top-up (see `docs/adr/0017-top-ups-are-the-one-sale-outside-a-subscription.md`). Create each Plan as a recurring price in Stripe with a lookup key (for example `pumpkit_pro_monthly`), and list that key in `BILLING_PLAN_KEYS` (see `docs/configuration.md`). Set each price's tax behaviour to inclusive, and set up Stripe Tax in test mode too: Checkout charges VAT and collects VAT IDs, so Stripe refuses to create one without it (see [Selling Plans](self-hosting.md#selling-plans)). Add a registration in test mode as well, or every test Checkout charges no tax. Checkout always passes `managed_payments[enabled]=false` (`billing/gateway.py`): whoever runs the Instance is the seller, and Stripe's Managed Payments, on by default for new accounts, would make Stripe the seller instead and refuse prices whose product has no tax code. Only the Plans in `BILLING_PLAN_KEYS` appear on the landing page and on the Paywall (`GET /api/v1/billing/plans`, which also returns the Allowance and the Trial's limits from the caps in settings, for the offer lines in `features/billing/planOffer.ts`), and Checkout (`POST /api/v1/billing/checkout`) takes nothing but a Plan key: the server resolves the price and always buys one. A User has at most one Running Subscription, and the backend enforces it: before deciding anything, Checkout syncs the User's Subscriptions from Stripe (`billing/service.sync_customer`), so it sees a Subscription no webhook has reported yet, and a User with a Running Subscription gets a `409 Conflict` (they manage it in the billing portal). A User who has never had a Subscription gets a Trial of `BILLING_TRIAL_PERIOD_DAYS` days, once, through that Checkout with a card; the client can't ask for one. The billing service answers both questions (`billing/service.get_subscription_offer`). Starting a Checkout cancels the User's `incomplete` Subscriptions and expires their other open Checkouts, so only the newest attempt can start a Subscription. A trialing User can end their Trial early with `POST /api/v1/billing/subscribe-now` (Subscribe now on the Usage card and the limit notice): it syncs first, refuses anyone not trialing with a `409`, ends the Trial through the gateway (`end_trial`, which sets Stripe's `trial_end=now` with `payment_behavior=allow_incomplete`), and syncs again, so the new billing cycle anchor starts the first paid Allowance period at once. A first charge that fails, or that waits for the User to authenticate it, leaves the Subscription past due as Stripe reports it and answers a `402` whose message covers both.

Subscribe the Stripe webhook to: `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded` and `charge.dispute.created`. Webhooks are nudges (ADR 0004): each of these events only names the customer that changed, and Pumpkit then lists that customer's Subscriptions or Top-ups from Stripe and syncs its copy, ignoring the event's payload. A dispute names only its charge, so the gateway looks up the charge's customer first.

Top-ups (ADR 0017) are one-off Checkouts (`POST /api/v1/billing/top-ups/checkout`, only while `BILLING_TOP_UP_KEY` is set) marked with `pumpkit_purchase=top_up` in their metadata. `billing/service.sync_top_ups` lists the customer's completed Checkouts with their charge expanded and adds the paid Top-ups it lacks, or marks refunded or disputed ones removed. `check_room_with_top_ups` and `charge_shortfall` in `billing/service.py` are how an area above billing spends one: check before the action, charge what the Allowance can't cover once the action is recorded, as `posts/version_writing.py` does for Generations. Scheduling charges X posts and link posts with `scheduling/top_up_charges.rebalance_top_ups` whenever a Scheduled post is created, changed, deleted or Failed: it charges every waiting and Failed Scheduled post of the User in each Allowance period involved afresh, in publish-time order, from the Top-ups bought by and still unexpired at each one's publish time, so the Top-ups pay exactly for the overflow. Its `check_room` runs that same charging as a dry run, before and with the new or changed post, and refuses when any post in the periods involved would be less covered than before, since an earlier post can push a later one onto a Top-up that has expired by then, or take the Top-ups a later period needs; a post already over a lowered limit blocks nothing that takes no room from it; both share `billing/top_ups.cover_in_order`. Each User's checks and charges run under a row lock on the User (`auth/service/users.lock_user_id`), held until the request commits. Each charge is a `TopUpCharge` row pointing at the Version attempt or Scheduled post it was for, and an area's count of what it used leaves out every charge, a removed Top-up's too. The rebalance keeps a post's charges on a removed Top-up (cut down to what the post still needs) and charges only the rest afresh. Deleting a Scheduled post with live Parts keeps them counting: `top_up_charges.keep_live_parts_counted` charges the post for its live Parts alone, detaches those charges (a `TopUpCharge` naming neither a Version attempt nor a Scheduled post stays spent) and records the rest in `UnscheduledLiveParts`, which `scheduling/service.x_posts_used_between` adds to the period's usage. A Top-up stores `NULL` for a count that had no cap when it was bought, and `0` when a small cap rounded down to none. Tests add a Top-up with `fake_billing.set_top_up(...)` and a signed `checkout.session.completed`.

Every Stripe call goes through the `BillingGateway` port (`src/pumpkit/billing/gateway.py`): only its Stripe adapter uses the SDK, it returns plain data, and any provider failure is a `BillingProviderError`, which the global handler returns as a 502 with an `error_id`. Routers inject it with `Depends(get_billing_gateway)`; tests get `FakeBillingGateway` through the autouse `fake_billing` fixture, which holds each customer's Subscriptions (`fake_billing.set_subscription(...)`) and signs webhook events (`fake_billing.signed_event(...)`) to post to the endpoint.

Every area route takes `current_user: User = Depends(require_subscribed_user)` (`src/pumpkit/billing/dependencies.py`), reads included: it returns a 403 to a User who isn't Subscribed, reading only Pumpkit's copy (ADR 0018). Only auth, the User's own account, billing, `/instance` and `GET /onboarding` take `get_current_user` instead. Tests make the `user` fixture Subscribed by requesting the `subscribed` fixture; `tests/test_paywall.py` lists the gated and the open routes. On the frontend nothing past the Paywall checks the Subscription: treat a 403 from a write as a cue to call `useSubscribed().refresh()` (or `useOnboarding().refresh()` outside `AppLayout`), which checks the Paywall again and so sends a User whose Subscription ended to it. Settings reloads billing on every visit, since Stripe changes it outside the app. The Stripe return routes (`/billing/success`, `/billing/cancelled`) go to `/` with the checkout status in the location state: `/` greets a success with confetti, waits a few seconds for the webhook if the Paywall still shows, and the Paywall says a cancelled checkout charged nothing.

An Instance without the Stripe billing group sells no Plans (ADR 0011): `billing/service.sells_plans()` is false, `require_subscribed_user` and the publisher's check let every User through (`billing/service.has_access`), and the billing routes and the webhook answer 404. The frontend reads `sells_plans` from `useInstance()`: `GET /onboarding` never answers `paywall`, and Settings' Plan card, the `/billing` routes and the landing page's pricing are left out. Tests switch billing off with the `sells_no_plans` fixture, or by rendering with an Instance whose `sells_plans` is false.

`billing/mediator.handle_webhook` owns the webhook transaction: it records the event for deduplication, locks the customer's User row, syncs the customer's Subscriptions (`billing/service.sync_customer`) or Top-ups (`billing/service.sync_top_ups`) from Stripe, depending on the event, and commits once. The lock is held across the Stripe call, so webhooks for one customer run one after another. Webhook handlers use the session they are given, never commit, and raise to roll back the whole event so Stripe retries it; a webhook for an unknown customer is logged and skipped.

### Write a Post

New post (`/new`) is where a User writes Posts. `POST /api/v1/posts` takes a Brief and answers with the Post and its first Version once both model calls are done, which can take a minute or two (the Caddyfile allows it). `posts/mediator.start_post` reads the corpus (the newest 20 stored posts of each of the User's Inspiration authors, in list order) through `posts/service.py`, ends the read transaction, writes the Version with `src/pumpkit/posts/writing/versions.py`, and only then stores the Post with its corpus post ids and the attempt, succeeded or failed. A failed attempt is committed before the error is re-raised, so it survives the request's rollback. The attempt keeps the Sketch, its model and its usage, but no Version response carries the Sketch.

A Post can start as a Thread: `format` on the request is `"post"` (the default) or `"thread"`. A Thread's sketch and humanizer calls use `prompts/sketch_thread.py` and `prompts/humanizer_thread.py` (which shares the single-post humanizer's guidelines) and answer `parts`, a list, instead of `post`. The humanizer reads the scrubbed Sketch as numbered `<part>` blocks (`prompts/parts.py`). Both prompts and the check after each call read `THREAD_MIN_PARTS` and `THREAD_MAX_PARTS` (2 and 10, `writing/constants.py`): a reply outside them, or with a blank Part, fails the attempt and is never cut. Tests script a Thread's writing call with `written_thread()`.

`POST /api/v1/posts/{id}/versions` takes Feedback and answers with the next Version. Only a Draft or a Failed Post takes Feedback (ADR 0015), so the route lives in `scheduling/router.py`: `scheduling/mediator.give_feedback` reads the Post's Scheduled post, refuses a Scheduled or Published Post with a 409 that names the fix (`scheduling/post_status.check_takes_feedback`), and owns the transaction around the model calls, checking the status again before it stores the Version. `posts/version_writing.prepare_next_version` reads the Post's stored corpus (not the User's current Inspiration authors) and its Versions, then runs the revision call: the sketch prompt, the corpus, the Brief, each Version's text as an assistant turn after the Feedback that produced it, and the new Feedback last. Each Feedback starts with the number of the Version before it and, when the Text it was given on (the Version's Starting text, ADR 0016) wasn't that Version as written, what the User did: "I went back to Version 1", "I changed the text to: …" or "I went back to Version 1 and changed it to: …" (`prompts/feedback.py`). Feedback is given on the Post's Text, read when the request arrives; the request may carry `text`, the Parts the browser shows, and is refused with a 409 when they aren't the saved Text, so the web app saves a pending edit first. The revision humanizer gets every earlier Feedback framed as already applied, the Starting text in place of the previous Version, the latest Feedback, and the sentences the User wrote by hand (`posts/writing/starting_text.hand_written_sentences`, a sentence diff against the Version the Text came from) marked to keep. Sketches and failed attempts stay out of that conversation. A Post with no Version (its first attempt failed) answers 409.

New post navigates to the Post's page, `/posts/:id` (`pages/PostPage.tsx`), once the first Version is written. The page reads `GET /api/v1/posts/{id}`, served from `scheduling/router.py` beside the Feedback route because a Post's status comes from its one Scheduled post (ADR 0015): the answer carries the Brief, every Version, `status` (`draft`, `scheduled`, `published` or `failed`, from `scheduling/post_status.py`) and the full `scheduled_post`, or null. The MCP tool `get_post` answers the same from `scheduling/tools.py`. On the page, `features/posts/usePost.ts` holds the Post and gives its Text and Versions to a `TextController` (`features/posts/text/`), which owns edits, autosave, undo, redo, restores and Feedback; the Text card shows the Post's Text (the Scheduled post's text once it has one), and one dock in `features/posts/panels/` follows the status. History (`features/posts/panels/HistoryPanel.tsx`) restores a Version through `POST /api/v1/posts/{id}/versions/{number}/restore`, which `scheduling/mediator.restore_version` gates like Feedback (`post_status.check_text_changes`) before it sets the Text from that Version; the `restore_version` MCP tool calls the same mediator. The Text card (`features/posts/TextEditor.tsx`) is editable in place on a Draft or a Failed Post; the controller shows each edit at once and saves it after a pause through `PUT /api/v1/posts/{id}/text` (`scheduling/mediator.edit_text`, the same gate, then the Part-count and live-Part checks), retrying a failed save. "Post to…" and Feedback flush a pending save first, and a restore drops it.

Feedback takes an optional `format`; without one the new Version keeps the Text's Format. The revision call runs under the new Format's sketch prompt and answers `revised_post` or `revised_thread`. Each earlier Version's text keeps its own Format in the conversation: a single post as written, a Thread as numbered `<part>` blocks so Feedback can name "Part 3". A Feedback that switched Format is framed as a rewrite into the new Format (`prompts/feedback.py`), both when it is new and when it is rebuilt into a later conversation. The revision humanizer runs under the new Format's humanizer prompt and gets the text the Feedback was given on in its own Format (`prompts/revision_humanizer.py`).

Both Formats are written for the post limit of the User's X account: `posts/version_writing.char_limit_for` reads the X connection's `subscription_type` and asks `x_connection/x_length.x_post_max_chars`, so 25,000 for Premium and PremiumPlus and 280 otherwise, or with no X connection. The sketch prompts and the Thread humanizer state it per Part (`sketch_post_prompt(char_limit)` and its siblings, cached so each limit sends one stable system prompt); the single-post humanizer stays v6's and states none. Each Part's `char_count` is X's weighted length and its `char_limit` the account's limit as it is now, the same one scheduling enforces. A Version's text over it is flagged, not refused.

The sketch and revision calls also choose and write the Hook. Their shared system prompt (`prompts/sketch_post.py`) says when to open with a library Hook and what makes one work, then holds the curated library and the hooks to avoid from `prompts/hook.py`. Both calls answer `hook_reasoning` (one to three sentences on the opening, generated first), `hook_name` (the library id, or null for an opening with no library Hook) and `post`. The attempt stores `hook_reasoning` and `hook_name`; `writing/versions.py` logs a name the library doesn't have and stores null in its place, and the Version is written either way. Tests script the writing call's reply with `written()` from `tests/posts/writing_replies.py`.

The prompts in `src/pumpkit/posts/writing/prompts/` are copied word for word from pumpkit-v6, `<creator>` corpus markup included, except for the sketch prompt's hook section, length rule and output fields and the humanizer's paragraph that keeps the Hook, which were written for Pumpkit. Change them only on purpose, as a prompt change. Each call's model is an `LLM_*_MODEL` setting (`core/config.py`).

### Schedule a post

On an Instance without `X_CLIENT_ID` and `X_CLIENT_SECRET`, `GET /instance` answers `x_connection: false` (`settings.is_x_configured()`): Onboarding has no X step, and the web app shows no control to connect or reconnect X. Read it from `useInstance()` before offering one. Backend tests set the keys with the `x_configured` fixture; the test environment leaves them unset.

A Subscribed User connects X in Onboarding's X step or in Settings' X account card (`x_connection/router.py` and `scheduling/router.py`; the X publisher port in `x_connection/x_publisher.py`). While X no longer accepts the X connection, `ReconnectXBanner` (`features/xConnection/`) sits above every page's header.

Every Scheduled post is copied from its Post's Text (ADR 0016), and a Post goes out once, so it has at most one Scheduled post (ADR 0015). The Post takes its status from it, never stored: none is `draft`, `scheduled` or `publishing` is `scheduled`, then `published` or `failed` (`scheduling/post_status.py`; the frontend mirrors it in `features/posts/postStatus.ts`). `scheduled_posts.post_id` is unique, so the database holds the rule too.

`POST /api/v1/scheduled-posts` takes a required `post_id` (the backend copies that Post's Text, one Part for a single X post, several for a Thread), either `publish_at` or `publish_now`, and a `community` (its ID or pasted URL) or none for the profile. It refuses typed `parts`, and refuses with a 409 a Post that already has a Scheduled post in any state, naming the fix: edit it, or unschedule it first. `PATCH` takes what changes: edited `parts` (every Part in order) or `copy_text` (the Post's Text again: its Parts after the live ones replace those not live), `publish_at` or `publish_now` (which publishes within the request, as on creation, and is how a Failed Post is retried), and a `community` string moves it to that Community, `null` back to the profile, and leaving it out keeps its Destination. `DELETE` removes a scheduled or Failed one, which makes its Post a Draft again; a Published one can't be deleted. There is no list of Scheduled posts: `GET /api/v1/posts` (in `scheduling/router.py`, since a Post's status comes from its Scheduled post) lists Posts by `status` with `limit` and `offset`, each with a summary of its Scheduled post, plus `counts` per status for the Posts tabs and the sidebar's Failed badge. `GET /api/v1/posts/{id}` has the full Scheduled post. On the web, `pages/Posts.tsx` shows one tab per status at `/posts/scheduled`, `/posts/drafts`, `/posts/published` and `/posts/failed` (`features/posts/list/`), and `PostCountsProvider` in `AppLayout` holds the counts: every tab page sets them, and `usePost.setScheduledPost` refreshes them after any change to a Post's Scheduled post.

The router and the MCP tools in `scheduling/tools.py` only map their arguments onto one mediator interface: `mediator.create_scheduled_post` takes a `NewScheduledPost` and `mediator.edit_scheduled_post` a `ScheduledPostEdit`, frozen dataclasses in `scheduling/rules.py`. `NewScheduledPost` always names a Post, and its constructor refuses both or neither of a time and publish now. `ScheduledPostEdit`'s refuses both Parts and `copy_text`, both a time and publish now, or nothing to change. An edit's Destination change is `KeepDestination`, `ToProfile` or `ToCommunity(pasted)`. The request schemas keep only wire concerns: field limits, aware datetimes, `extra="forbid"`.

On creation, the mediator then checks, in order, the X connection (`connection_to_publish_on`), the Post (the User's, with a Text), that it has no Scheduled post yet, the length (`rules.check_length`, X's weighted count), the time (`rules.check_publish_at`: a whole minute, one minute to a year ahead, stored in UTC) and the room for it (`check_x_posts_room`, which counts Parts: each is one X post, and one with a link also a link post, against the Allowance period where Plans are sold and the UTC calendar month otherwise). Only then does it look up the Community's name through `XReader`, so a refused request makes no twitterapi.io call; an unknown Community is refused, and a failed or unconfigured lookup stores no name.

Test a rule in `backend/tests/scheduling/test_mediator.py`, and keep one case of each refusal in the route and tool suites; ADR 0015's rules have their own suite, `test_a_post_goes_out_once.py`. `post_with(*parts)` (a fixture in `tests/conftest.py`) seeds a Post with one Version as its Text and returns the Post's id, and `next_version(post_id, *parts)` adds the next Version to the same Post and makes it the Text. `await connect_x()` (a fixture in `tests/conftest.py`) gives `user` an X connection to `fake_x_publisher.account` without the authorization's requests, at the time `get_clock` reads, so request the clock fixture first.

On the web, the "Post to…" dialog (`features/posts/postTo/`) sends a Post to X. On a Draft it creates the Scheduled post with only the `post_id`, once any edit is saved, so the server copies the Text on screen. On a Failed Post it patches the Failed Scheduled post instead, with `copy_text` and the new time or `publish_now`; live Parts show locked, and the Text's Parts in their places are skipped. Each case is a `PostToSender` in `postTo/senders.ts`. A Scheduled Post is edited inline on its page (`features/posts/edit/`): its Parts become text boxes in the Post's card, saved with `PATCH`, and Unschedule sends `DELETE`. The backend refuses a Post that isn't the User's. The X connection's provider sits in `AppLayout`, so every page and the Reconnect X banner share it.

A Scheduled post for later waits in `scheduled` until the publisher picks it up. The publisher is a process of its own (ADR 0007): `python -m pumpkit.scheduling.publisher`, the `publisher` service in `compose.dev.yml` and `compose.yml`. Every `PUBLISHER_POLL_INTERVAL_SECONDS` it runs `publisher.run_pass`, which:

1. fails Scheduled posts stuck in `publishing` for over 10 minutes with "Check your X profile" (`scheduling/publishing.recover_stuck`: a publisher died mid-call; one whose Parts are all live becomes Published instead);
2. claims and publishes the soonest due one (`scheduling/publishing.publish_next_due`, which claims through `scheduling/service.claim_next_due`: `FOR UPDATE SKIP LOCKED` on Postgres, and a conditional update that keeps the claim single anywhere);
3. repeats until nothing is due.

`scheduling/publishing` owns every commit of a publish: it commits the claim and any rotated refresh token before calling X, then calls X once per Part not yet live, in order, each Part after the first as a reply to the one before (ADR 0014). It commits each Part's X post id as soon as X accepts it, and Published once every Part is live, or Failed. Its steps live in `scheduling/publish.py`, which flushes and never commits. A 429 or a refused connection (to publish or to refresh the token) means X surely didn't publish that Part, so it goes back in `scheduled`, keeping the Parts already live, with a doubling backoff from one minute for the publisher to retry, and becomes Failed if it still can't go out 15 minutes after its publish time. Post now publishes within the request through the same `scheduling/publishing` module; when X doesn't take it, the request returns it in `scheduled` and the publisher retries it like any other. A retry or a reschedule starts at the first Part that isn't live, as a reply to the last live one. A refused Part or an unknown outcome makes it Failed, with a reason that names the Part in a Thread. Live Parts are locked: an edit's `parts` must open with them unchanged (`rules.check_live_parts_kept`, a 409 otherwise), and `service.edit` replaces only the Parts that aren't live.

Test the pass by calling `run_pass(db_session_maker, fake_x_publisher, fixed_clock)` directly and checking outcomes with `scheduled_posts(client)` from `backend/tests/scheduling/reading.py`, which reads them through `GET /api/v1/posts` (see `backend/tests/scheduling/test_publisher.py`). The `fixed_clock` fixture freezes time at a known instant for tests that write out dates. Under SQLite the row lock is a no-op, so tests of concurrent passes exercise the conditional claim.

### Refuse a request

A mediator serves both the web routes and the MCP tools, so it refuses with one of the bases in `core/errors.py` rather than an `HTTPException`: `NotFoundError` (404), `ConflictError` (409), `RefusedError` (422) or `BadRequestError` (400). Each takes the `detail` the User reads, word for word on the web and in a tool error. Pass `fix_page`, a web app path, when the User fixes the refusal in the web app, as the X connection refusals do with `fix_page=X_CONNECTION_PAGE` (`/settings`, in `scheduling/mediator.py`): the HTTP body then carries the full URL as `url` beside `detail`, built from `PUBLIC_URL`, and a tool error appends it to the text. Raise a base directly, and subclass it only when some code catches that refusal. An MCP tool reads an `HTTPException` as an unexpected error, so only web-only code such as `auth` raises one. Scheduling's pure rules raise `RuleBroken` (a `RefusedError`) and `MonthFull` (a `ConflictError`) from `scheduling/rules.py`.

### Add an MCP tool

Claude Code reaches Pumpkit through the MCP endpoint at `POST /api/v1/mcp` (ADR 0012; the user guide is `docs/claude-code.md`). A tool lives in its area's `tools.py`, beside the router, and calls only that area's mediator, as the router does. `authors/tools.py` is the example to copy.

1. Write the tool as an async function whose first parameter is `call: ToolCall[User]` (`core/mcp_tools.py`), followed by the tool's arguments. Its name is the tool's name (a snake_case verb), its docstring is the description Claude Code reads, its arguments become the input schema, and its return type, a response schema, becomes the output schema. `call.user`, `call.db` and `call.now` are what a route gets from `get_current_user`, `get_async_db` and `clock()`; `await call.provide(get_x_reader)` gives any other provider, honouring the app's dependency overrides, so the tests' fakes apply.
2. Validate input as the route does: build the route's request schema (`InspirationAuthorAddRequest(handle=handle)`) so its checks and messages are the same.
3. Add an `McpTool(fn, rate=..., annotations=...)` to the module's `TOOLS` list. Use the web route's rate where it has one, through the area's `WRITE_RATE` in `schemas.py`, and `READ_ONLY_RATE` for tools that only read. Pick `READ_ONLY`, `ADDITIVE` or `DESTRUCTIVE`: clients ask the User before a destructive tool, and treat a tool without annotations as destructive. Every tool is refused to a User who isn't Subscribed (ADR 0018). A browser-only tool just answers with a web app link, as a `LinkToolResponse` (`core/schemas.py`): `connect_x` in `scheduling/tools.py` and `manage_subscription` in `billing/tools.py`.

`pumpkit/mcp_server.py` registers every module's `TOOLS` and wraps each tool: it counts the call against the User's limit for that tool, checks access with `billing/service.has_access` (a tool error with the subscribe link otherwise), opens the call's session, and turns what the tool raises into a tool error. An `AppError` or a request schema's `ValidationError` keeps the web route's `detail` word for word, then the fix page's `url` when there is one, and `retry_at` when there is one; a reported error goes to PostHog with an `error_id`, as the global handler sends it. So a tool raises the mediator's refusals and never catches them. Tool calls send no product events (ADR 0012).

import-linter lets only `pumpkit.mcp_server` import a tools module, and keeps a tools module from importing its router or the router from importing it.

Test a tool through the endpoint with the `mcp` fixture: Claude Code connected with an API key that `user` created through `POST /api/v1/api-keys` after a real sign-in, on a client without the `get_current_user` override. Request `subscribed` or `sells_no_plans` before it, since creating a key needs access. `await mcp.call_tool("add_inspiration_author", handle="levelsio")` returns the result, with `structuredContent` holding the response schema; `error_text(result)` (`tests/mcp_client.py`) asserts a tool error and returns its text. See `backend/tests/authors/test_inspiration_author_tools.py`.

### Call an LLM

Set `LLM_API_KEY` (and `LLM_BASE_URL` for an endpoint other than OpenRouter). Mediators reach models through the `LLM` port (`posts/llm.py`): the router injects it with `llm: LLM = Depends(get_llm)` and passes it to the mediator, which calls `await llm.structured(model=..., messages=..., response_model=MyPydanticModel)`. Any provider failure is an `LLMError`, which the global handler returns as a 502 with an `error_id`; a missing key is a 503 naming the variable. Tests get the scripted `FakeLLM` through the autouse `fake_llm` fixture: queue `fake_llm.replies` and read the messages each call received in `fake_llm.calls`.

The port wraps `llm_client` (`posts/llm_client.py`), which also has `llm_complete(...)` and `llm_stream(...)` (yielding `StreamDelta`, `ToolCallDelta`, `AssembledToolCall` and `ModelUsage`) for calls that don't fit it.

### Ask Jev a question

A labelled question goes to Jev, not to an LLM (ADR 0013). Set `TYPESAFE_API_KEY` to try it for real. Mediators reach Jev through the `Classifier` port (`core/classifier.py`): a router injects it with `classifier: Classifier = Depends(get_classifier)` and passes it to the mediator, which asks:

```python
classification = await classifier.classify(
    state={"conversation": [...]},
    questions={"opening": ChoiceQuestion(instructions="...", criteria={"new_hook": "...", "keep_hook": "..."})},
    model=settings.TYPESAFE_MODEL,
)
answer = classification.answers["opening"]  # a ChoiceAnswer: choice, confidence, probabilities
```

`state` is any JSON value, and each question's name keys its answer. `classification.model` is the Jev version that answered, and `classification.usage` its token counts. The adapter waits 5 seconds and retries once on a timeout, a lost connection, a 429 or a 529. Jev is optional, so the caller catches `ClassifierError` (the provider failed or gave an answer that doesn't fit the questions) and `ClassifierNotConfiguredError` (no key), a subclass of it, and takes its cautious path instead of failing the request. Tests get the scripted `FakeClassifier` through the autouse `fake_classifier` fixture: queue `fake_classifier.replies` (answers by question name, or an exception) and read each call's state, questions and model in `fake_classifier.calls`. With no reply queued it raises `ClassifierError`, so a test that doesn't script Jev sees the cautious path. The adapter's own tests are in `backend/tests/core/test_classifier.py`.

### Copy a photo into a User's Photo

A User's Photo is always a copy stored in `users.avatar_data_url`: the browser never loads it from Google, Gravatar or X. Mediators download one through the `PhotoFetcher` port (`core/photos.py`): a router injects it with `photo_fetcher: PhotoFetcher = Depends(get_photo_fetcher)`, and `await photo_fetcher.fetch(url)` returns a JPEG data URL, a centred square of at most 256px within the upload limits, or `None` when the image is missing, too large, not an image or unreachable. It never raises, so the caller carries on without a Photo. Store the result through auth's service: `fill_photo` for a Photo the User didn't pick, which applies only while `may_fill_photo` (no Photo and no `photo_chosen_at`) and leaves the marker unset, or `choose_photo` for one they picked, which sets `photo_chosen_at` so Pumpkit never fills it again. Tests get `FakePhotoFetcher` through the autouse `fake_photo_fetcher` fixture: map URLs to data URLs in `fake_photo_fetcher.photos` (any other URL reads as a failed download) and read the URLs asked for in `fake_photo_fetcher.fetched`. The adapter's own tests are in `backend/tests/core/test_photos.py`.

### Add a page to the shell

Add its route to `signedInRoutes()` in `frontend/src/pages/signedInRoutes.tsx`, which both `App.tsx` and the page tests mount inside `AppLayout`, and give the page a `Topbar` with its title and any header controls as `actions`. A page the sidebar links to also goes in `SIDEBAR_PAGES` in `frontend/src/features/sidebar/pages.ts`. `frontend/src/pages/AppLayout.tsx` holds the shell and the state pages share: the Persona, the X connection and the Post counts. ### Changing the Terms or the Privacy Policy

Each document is a Markdown file per language in `frontend/src/features/legal/documents/` (`terms.en.md`, `terms.it.md`, `privacy.en.md`, `privacy.it.md`), listed with its route and "Last updated" date in `frontend/src/features/legal/documents.ts`. Both languages are equally valid, so they must always say the same thing.

1. Edit the English and the Italian file in the same change, keeping the same sections, clause numbers and `{#anchor}` ids. Links point at those anchors, such as the consent banner's link to `/privacy#cookies`.
2. Set `TERMS_LAST_UPDATED` or `PRIVACY_LAST_UPDATED` in `documents.ts` to the day of the change. Both language versions read it, so the two pages show the same date. For the Terms, set `TERMS_VERSION` in `backend/src/pumpkit/billing/terms.py` to the same date in the same change: checkout refuses any other version with a 409, so Users accept the new Terms before their next checkout (ADR 0010). If a clause the Paywall's checkboxes cite moves or is renamed, update `ONEROUS_CLAUSES` and the withdrawal link in `frontend/src/features/billing/TermsAcceptanceFields.tsx`.
3. For a material change, email every User at least 30 days before it applies, as clause 19 of the Terms and the last section of the Privacy Policy promise.

When you add a cookie or a browser storage key (a `storage.ts` key, a cookie the backend sets, or one a new third-party script sets), add a row for it to the cookie tables in both Privacy Policy files, under strictly necessary or Analytics consent, and follow the steps above.

### Branding

To rebrand, change `APP_NAME`, the meta tags and JSON-LD graph in `frontend/index.html`, `frontend/src/assets/brand/*.svg` (`mascot.svg`, the static pixel mascot, and `wordmark-{light,dark}.svg`, the README wordmark as outlines, shown only while `APP_NAME` is Pumpkit; any other name is set in Inter), `frontend/public/*.png`, `backend/src/pumpkit/auth/templates/emails/assets/*.png` (PNG renders of the brand SVGs for the Magic link email, which mail clients need: `rsvg-convert -h 100 mascot.svg`, `-h 66` for each wordmark), and the design tokens in `frontend/src/index.css`. The tokens live under `:root` (light) and `.dark`, with the same names in both. Colours are HSL triples: surfaces (`background`, then `card`, the raised surface of a card, `popover` and `muted`), the pumpkin `primary`, and the status colours `destructive`, `success` (olive) and `warning`; they derive from the brand palette (Pumpkin `#D96B45`, Charcoal `#20201E`, Ivory `#F7F5EF`, Olive `#66734E`). `background` is the canvas the sidebar sits on and `card` the raised panel each page sits on, which Tailwind exposes as `text-destructive` and the like. `--hover` (the wash under a hovered control) and `--trace` (the Pumpkin trace an undo, redo, restore or rewrite leaves on the words it changed) are `rgba` colours read with `var()`, `--primary-gradient` (the primary button) and `--primary-gradient-soft` are CSS gradients, and `--shadow-raised` and `--shadow-panel` are the `shadow-raised` and `shadow-panel` utilities. Character counters on the Post's page use Inter's tabular figures; the others use the mono font, `fontFamily.mono` in `tailwind.config.ts`. `src/theme.test.ts` fails when the two modes define different names or a text pairing drops below 4.5:1.

## Testing

```bash
make test   # backend pytest and frontend vitest
make e2e    # starts the dev stack if it is down, then runs Playwright against it
```

Before the first `make e2e`, run `cd e2e && npm install && npx playwright install chromium`. CONTRIBUTING lists every target.

`make smoke` builds and starts the production stack from `.env`, then runs `scripts/check-stack.sh` against it. To check a stack that is already running, run `sh scripts/check-stack.sh [BASE_URL]` (default `http://localhost:8080`; it needs curl). Set `POSTHOG_RELAY=true` when the stack runs the PostHog relay, and `EXPECT_SEARCH_INDEXING=true` when it has `ALLOW_SEARCH_INDEXING=true`.

The e2e suite opens Settings' Plan card, so its Instance must sell Plans: set the Stripe billing group in `.env`. [CONTRIBUTING](../CONTRIBUTING.md#make-targets) gives dummy values that work.

If host port 5432 is already taken, add a local compose override that remaps the db service and point `COMPOSE_FILE` at it:

```yaml
# compose.dev.override.local.yml
services:
  db:
    ports: !override ["55433:5432"]
```

```bash
make dev DEV_COMPOSE="docker compose -f compose.dev.yml -f compose.dev.override.local.yml"
```
